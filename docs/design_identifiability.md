# 識別性ベースの匿名化 — 仕様再設計（v0.8.0 で Phase 1 実装済み）

作成: 2026-09-02　状態: **承認済み（2026-09-02）。Phase 1 実装完了（v0.8.0、§6 参照）**。§7 の未決事項は既定値で実装し、設定で変更可能

## 0. 結論

| 論点 | 結論 |
|---|---|
| 何を匿名化するか | **私人を識別する情報**（私人名、私人に帰属する準識別子、番地以下の住所、連絡先・ID）。公人名・公知の地名/施設/組織は原則そのまま残す |
| 「自動で区別」か「事前に度合いを選ぶ」か | **両方を層にする**。事前に `level`（strict / standard / minimal）で上限を決め、standard の中で公知判定と帰属検出が自動でケース分けする |
| 実現方式 | 検出→解決の後、Policy の前に **注釈ステージ**を挟み、エンティティ型をサブタイプ（`PERSON_PUBLIC` 等）に書き換える。Policy は既存機構のまま。Policy にサブタイプの規則が無ければ既定演算子（マスク）に落ちる = **fail-closed** |
| 公知の判定材料 | Wikipedia 見出し語（246万件）: 実在の公人/組織/地名を 90%以上拾い、架空の組織/施設/住所の誤ヒットは 1%未満（§4.1）。人物はさらに **Wikidata の知名度（sitelinks 数）** で絞る（§4.5） |
| 既定値の推奨 | ライブラリ既定は **strict（現行と同じ挙動）**。LLM 学習データ用途では明示的に `standard` を選ぶ |
| モデル再学習 | **不要**。NER は従来どおり「候補を漏らさず拾う」役割に留め、識別性の判断は後段ルールに置く |

現行仕様（全エンティティを置換）の出力例。公人や公知が偽物に置き換わり不自然で、LLM 学習データとしても有害:

```
岸田首相と会食した山本部長は大阪へ → 池田首相と会食した川口彩花は<LOCATION_001>へ
```

実装後の出力（`examples/try_privacy_masker.py --level standard --device cpu`、当時の本番モデル（token 分類 30m）・語尾拡張あり。偽名は鍵に依存）:

## 1. 仕様の再定義

### 1.1 匿名化対象の3分類

| 分類 | 定義 | 例 | 扱い |
|---|---|---|---|
| **直接識別子** | それ単体で特定の私人を識別する | 私人の氏名、電話、メール、口座・会員番号、番地以下の住所 | 常に匿名化（全レベル） |
| **準識別子** | 私人に結び付いたときに識別性を持つ情報 | 「田中さんの最寄りは西新宿五丁目駅」の駅、勤務先の支店名、在住の町名、賃借物件のビル名 | standard で匿名化。判定は帰属検出（§3.4） |
| **公知情報** | 誰でも知り得る公的事実で、個人の識別に寄与しない | 公人名（安倍元総理）、著名な地名・施設・組織（新宿駅、東京都庁、トヨタ自動車） | standard / minimal で保持 |

個人情報保護法の「特定の個人を識別することができるもの」に沿った定義。法人名はそもそも個人情報ではないが、機密として隠したいケースは strict で対応する。

### 1.2 エンティティ別の扱い

| 型 | strict（現行） | standard | minimal |
|---|---|---|---|
| PERSON（私人） | 匿名化 | 匿名化 | 匿名化 |
| PERSON（公人） | 匿名化 | **保持** | 保持 |
| LOCATION / FACILITY / ORG（公知） | 匿名化 | **保持**。ただし私人に帰属（§3.4）なら匿名化 | 保持 |
| LOCATION / FACILITY / ORG（非公知） | 匿名化 | 匿名化（現行どおり） | 保持 |
| ADDRESS | 全体を置換 | **市区町村（任意で町名）まで保持、番地・建物・部屋を置換** | 同左 |
| EMAIL / PHONE / ID 等 | 匿名化 | 匿名化 | 匿名化 |

「公人」「公知」は**正の証拠があるときだけ**成立させる（§3.2, §3.3）。証拠が無ければ私人・非公知として扱う（fail-closed）。

### 1.3 レベル（事前選択）の意味

- **strict**: 現行と同一。判定データ不要。安全側の既定値。
- **standard**: 上表のとおり。LLM 学習データの自然さと私人保護の両立を狙う本命。
- **minimal**: 直接識別子のみ。帰属検出も行わない。統計・研究用途で文脈を最大限残したいとき。

レベルを先に選ぶ理由は予測可能性。自動判定だけに委ねると「なぜ残った/消えたか」が利用者に見えず、証拠不足時の挙動も定義できない。逆にレベルだけでは「新宿駅の周辺」と「最寄りの新宿駅」を分けられない。上限をレベルで、個別判断を自動で、という分担にする。

## 2. アーキテクチャ

```
Detector群 → Refiner → EntityResolver → [新] Annotator群 → Policy(operator_for) → Operator
                                          IdentifiabilityAnnotator:
                                            PERSON        → PERSON | PERSON_PUBLIC
                                            LOCATION/...  → LOCATION | LOCATION_PUBLIC
                                            (ADDRESS/EMAIL等は素通し)
```

- **Annotator** = `annotate(text, entities) -> list[Entity]` を持つ純関数的なステージ。`PrivacyEngine(annotators=[...])` で受け取り、`detect` / `transform` / `transform_batch` のすべてで resolve 直後に適用する（engine.py の `_annotate`）。位置を変えた・範囲外・型が空の出力は `AnnotatorError`（原文はメッセージに載せない）。
- **サブタイプ書き換え**を選ぶ理由: `Entity` / `Policy` の変更が不要で、既存 Policy の「未知の型は default に落とす」性質がそのまま **fail-closed** になる。利用者が `Policy` に `PERSON_PUBLIC: Keep()` を書かない限り従来どおりマスクされる（保持はオプトイン）。
- `Policy.preset("standard")` / `preset("minimal")` は `*_PUBLIC → Keep`（`public_types` で対象を調整）だけを持ち、それ以外は default でトークン化する。マスク方法（Surrogate、`keep="city"` の住所など）は利用者が `rules` に足す。`Policy.preset("strict")` は現行と同じ。
- 注釈は `TransformedEntity.entity_type` にそのまま現れるので、`--show-entities` で「なぜ残したか」が追える。

利用イメージ:

```python
from privacy_masker import IdentifiabilityAnnotator, PrivacyEngine, Policy, PublicKnowledge
from privacy_masker.operators import Surrogate

knowledge = PublicKnowledge.load("jawiki_titles_ns0.pmk")   # tools/build_knowledge.py で生成
policy = Policy.preset("standard")                           # *_PUBLIC → Keep、それ以外はトークン化
policy.rules.update({
    "PERSON": Surrogate(kind="person", key=KEY),
    "ORG": Surrogate(kind="org", key=KEY),
    "ADDRESS": Surrogate(kind="address", key=KEY, keep="city"),
})
engine = PrivacyEngine(
    detectors=[ner, regex], refiner=MorphologicalRefiner(), policy=policy,
    annotators=[IdentifiabilityAnnotator(level="standard", knowledge=knowledge)],
)
```

## 3. 各コンポーネント

### 3.1 PublicKnowledge（判定データ）

- **Wikipedia 日本語版 見出し語（ns0）**: 2,464,443 件。正規化（`_`→空白、全角空白統一）して 64bit ハッシュにし、ソート済み配列 + 二分探索で照合。約 20MB（括弧付き曖昧さ回避・年号・一覧を除くと 203万件・16MB）。Bloom フィルタ（3MB）は偽陽性 1% が「私人を公知と誤る=漏れ方向」なので採用しない。
- **Wikidata 人物（P31=Q5、日本語ラベルあり、sitelinks ≥ 閾値）**: 公人の許可リスト。閾値は §4.5 の観測から 10 前後を初期値にし、評価で調整する。
- 配布: 公知データ（`.pmk`）はリポジトリにも wheel にも同梱しない。利用者が `tools/build_knowledge.py` で生成し、`PublicKnowledge.load(path)` か環境変数 `PRIVACY_MASKER_KNOWLEDGE` で渡す（別パッケージでの配布は将来案、未実装）。strict では不要。
- 構築スクリプト `tools/build_knowledge.py`（見出し語ソースはデータフォルダ `PRIVACY_MASKER_DRIVE_DIR` に置いた Wikipedia 見出し語ダンプ（jawiki ns0、gzip テキスト、2026-09-02 取得））。

### 3.2 PublicFigureClassifier（PERSON の公人判定）

以下のいずれかを満たすときだけ `PERSON_PUBLIC`:

1. **公職肩書きが直後に隣接**: 総理・首相・元総理・大臣・長官・知事・市長・区長・町長・村長・議員・議長・党首・総裁・幹事長・大統領・国王・女王・外相・官房長官・総書記 など。裸姓でも成立（安倍元総理、岸田首相）。**企業肩書き（社長・部長・課長・代表）は不成立**（私人）。「氏」「さん」も不成立。
2. **フルネームが人物許可リストに一致**: 表層が 4 文字以上、または空白・中黒を含むこと（§4.2: この条件で架空私人の誤ヒット 0/292）。裸姓（田中・安倍）は許可リストの対象外（見出し語の 46.9% が姓のページと衝突するため）。

### 3.3 PublicKnowledgeFilter（LOCATION / FACILITY / ORG の公知判定）

- 表層（空白正規化後）が見出し語に一致すれば公知候補。「京都府京都市」「九州新幹線新大牟田駅」のような複合形は末尾要素（京都市・新大牟田駅）でも照合する。
- **正の証拠が無ければ非公知**（架空の会社・倉庫・支店はこれまでどおり匿名化）。プロトタイプ初版にあった「文書内に私人がいなければ残す」分岐は、NER の型誤り（「田淵案件」→ORG）を漏れに変えるため**採用しない**（§4.6）。
- **4 文字以下の英字のみの表層（NKS・NDS 等の略称）は見出し語に一致しても公知としない**。架空企業の略称が無関係な記事名（NDS = Nintendo DS）と衝突するため（§4.6）。
- 公知でも **帰属（§3.4）が成立すれば匿名化**が優先。

### 3.4 AttributionDetector（私人への帰属）

- 私人 PERSON から前後 40 文字以内にあり、かつ手掛かり語（最寄り・在住・勤務・勤務先・通学・自宅・実家・出身・通院・かかりつけ・所属・住所・居住・転居・本籍・配属・通勤・在籍・入院）または帳票ラベル（`住所:` `勤務先:` 等）が近傍にある → 帰属あり。
- 実測（§4.4）: 実在ニュース 170 件で誤帰属 0、私人文書では明示的な帰属（「居住地：那覇市内」「旧住所(横浜)」）を拾う。構造的な帰属（賃貸契約書の物件ビル名）は拾えないが、そうしたビル名は見出し語に無いので §3.3 で匿名化される。
- 残るのは「公知の場所 + 私人 + 手掛かり語なし」（「田中さんと新宿駅で待ち合わせ」）。standard では保持する。これを許容できないケースは strict を選ぶ。

### 3.5 住所の粒度

- `Surrogate(kind="address", keep="city")`: 正規表現で `都道府県 + 市区町村（郡・政令市の区を含む）` を切り出し（実測 98%、§4.4）、その部分は原文を残し、町名・番地・建物・部屋を既存の偽住所生成で置換する。切り出せない形（市名から始まる、複数行）は全体置換に落とす（fail-closed）。
- `keep="town"`（町名まで保持）は Phase 2。町名に漢数字（六本木・三田・二子玉川）が含まれ得るため、正規表現だけでは安定に切れない。
- 偽住所の建物名は、原文に建物・部屋の表記（号室・階・ビル・ハイツ等）があるときだけ付ける（v0.8.0 で実装。従来は長さ > 18 文字で付けていた）。
- **住所成分ガード（2026-09-09 追加、`IdentifiabilityAnnotator(address_guard=True)` が既定）**: NER は「番地があれば ADDRESS、なければ LOCATION」で学習しているため（学習データ実測 ADDRESS 4,698 件の 100% が番地付き）、住所の町名部分が LOCATION として出力され、jawiki 見出し語に一致すると `LOCATION_PUBLIC` = Keep になり、番地だけマスクされて町名が平文で残っていた（4 評価セット・standard で本物の住所 122 文字、minimal で 511 文字）。住所文脈の**正の証拠**（表層の丁目・番地・号室、ADDRESS / POSTAL_CODE エンティティとの重なり・助詞を挟んだ隣接、直前直後の番地、〒・郵便番号、`住所:` 等の帳票ラベル）があり、かつ市区町村以上（末尾が `都道府県市区郡`、`加茂郡川辺町` のような自治体）でない場所エンティティを公知判定から外す。法人格を含む組織名は例外。`minimal` でも適用し、`strict` は不変。実測: standard で本物の住所の漏れ 122→29 文字（token 分類モデル）/ 94→14（文字ヘッドモデル）、代償は正しい Keep の 0.55% / 0.29%。minimal では 511→139 / 467→118、代償 6.8% / 5.5%。

### 3.6 Refiner への追加（今回の測定で見えた境界問題）

- **分裂した名前の結合**: 空白・中黒で区切られた隣接 PERSON 断片を 1 スパンに（「網代 汐里」が「網代」「汐里」に割れる）。
- **地名/施設と誤認された姓の救済**: LOCATION/FACILITY/ORG スパン直後（空白 1 個以内）に短い PERSON スパンが続くとき、全体を PERSON にする（「生源寺 タキ」の「生源寺」が寺院名として FACILITY_PUBLIC になった）。
- **企業肩書きの切り離し**: PERSON スパン末尾の 部長・課長・社長・主任・係長・取締役 等を外す（「山本部長」が 4 文字フルネーム扱いで「松田美優」に置換された）。
- **種別語尾・法人格プレフィックスへの拡張（v0.8.0 で実装、`refiner_affix.py`）**: NER が固有名部分だけを検出した複合名（水戸▮データセンター、仙台▮地方裁判所、株式会社琉伸▮メディカルサポート、社会福祉法人▮ひだまり会）を、隣接する種別語尾・法人格まで広げる。ORG / FACILITY / LOCATION のみ、隣接エンティティで停止、PERSON は対象外。総当たり 46,200 件で欠け 0。公知判定側は法人格を外した表層でも見出し語を引く。
- いずれも `stress_truncation.py`（46,200 件）を通してから採用する（Refiner 変更の必須手順）。

## 4. 実験結果（判断の根拠）

評価データ（データフォルダ内、非公開）: 実在ニュース（wikinews 178 文書、公知が多い）、架空の私人文書（282）、固定 OOD（8 ジャンル 80）、実文書・難例セット（69）。モデルは初期モデル（token 分類 30m）、CPU。

### 4.1 Wikipedia 見出し語は公知の判定に使えるか

| 型 | 実在ニュースでのヒット率（高いほど良い） | 架空私人文書での誤ヒット率（低いほど良い） |
|---|---|---|
| PERSON | 91.9%（57/62） | 18.5%（93/502）→ 裸姓が原因。§4.2 で解消 |
| ORG | 91.5%（107/117） | 0.4%（1/247） |
| FACILITY | 70.4%（19/27） | 0.9%（2/229） |
| LOCATION | 90.9%（130/143） | 66.7%（50/75）→ 誤りではない（恵那・姫路など実在都市名を架空文書が使っている） |
| ADDRESS | — | 0.0%（0/88） |

非ヒットの公知は複合形（京都府京都市、九州新幹線新大牟田駅、旧京都府警本部）が中心で、末尾要素照合で改善できる。

### 4.2 PERSON 許可リストの条件

| 条件 | 架空私人の誤ヒット | 実在ニュースの網羅 |
|---|---|---|
| 裸姓（2 文字以下） | 46.9%（67/143） | — |
| 3 文字以上 | 7.2%（26/359）: 阿久津・五百川・布施川（3 文字姓）、あざみ・カナエ（名）、グエン | — |
| **4 文字以上 または 空白・中黒あり** | **0.0%（0/292）** | 89.5%（34/38） |

裸姓は肩書きルール（§3.2-1）で補う。

### 4.3 公職肩書きルール単独の網羅率

実在ニュースの PERSON 62 件のうち公職肩書きが隣接するのは 18 件（29%）。内訳: 大統領 7、総理 4、首相 4、市長 1、国王 1、議員 1。「氏」10 件は公私どちらにも付くため証拠にしない。肩書きルールは許可リストの補助であり単独では不足。

### 4.4 帰属検出と住所分解

| 項目 | 結果 |
|---|---|
| 帰属あり判定（私人文書 LOCATION/FACILITY 85 件） | 3 件（中央公民館別館・旧住所(横浜)・居住地：那覇市内） |
| 帰属あり判定（実在ニュース 170 件） | 0 件（誤帰属なし） |
| 住所の粒度分解（都道府県・市区町村・以下） | 124/127（98%）。失敗は市名始まり 2 件と複数行 1 件 |

| 名前 | Wikidata | sitelinks |
|---|---|---|
| （架空文書の代表社員と同名の、sitelinks 1 件の無名の実在人物の例。氏名・ID は伏せる） | — | 1 |
| 山田太郎 | Q11470294 | 2 |
| ハン・ソヒ（俳優） | Q41864388 | 25 |

sitelinks 閾値で「たまたま記事がある無名の同名人物」を許可リストから外せる。閾値 10 なら上 2 行（無名の同名人物・山田太郎）は私人扱い、ハン・ソヒ以上は公人扱い。

### 4.6 安全コスト（提案ルールで保持される gold PII）

ライブラリ実装（`IdentifiabilityAnnotator` + データフォルダの `jawiki_titles_ns0.pmk`、282 万エントリ）での測定。`tools/eval_identifiability.py` で再現できる。保持は見出し語ヒット / 公職肩書きの正の証拠があるときだけ。**最終値は当時の本番モデル（token 分類 30m）・語尾拡張 Refiner（数字語尾込み）で 2026-09-03 に再測定したもの**（初期実装時は初期モデルで測定。差分は下の注記）。

| セット | 過剰マスク文字数 strict→standard | 保持される gold PERSON | 保持される gold ORG / FACILITY / LOCATION |
|---|---|---|---|
| 私人: eval_ood_v1（80） | 713 → 670 | 10/164 | 17/86 ・ 4/66 ・ 15/19 |
| 私人: eval_real+hard（69） | 185 → 178 | 2/77 | 2/41 ・ 2/24 ・ 5/11 |
| 私人: 合成文書（282） | 453 → 430 | 3/502 | 8/247 ・ 8/229 ・ 39/75 |
| 公知: wikinews（178） | **72 → 20** | 40/62（望ましい保持） | 96/117 ・ 17/27 ・ 117/143（望ましい保持） |

注記:
- 初期モデルで測った初期値は wikinews 77 → 14、私人 PERSON 保持 18 件（9+2+7）だった。当時の本番モデルでは私人 PERSON 保持が **15 件（10+2+3）** に減り、strict の過剰マスクも 948→713・815→453 と大きく減った。
- ORG / FACILITY の保持増（13→17、1→8 等）の大半は、NER が複合名を分割して検出し、残った一般名詞部分（「株式会社アオバ情報システム」の情報システム、「ハシバ事務機リース株式会社」のリース）が見出し語に一致して公知扱いになるもの。識別に寄与する固有名部分は置換されており、私人保護の観点では問題にならないが、出力の見た目は「株式会社北斗建設情報システム」のようになる。法人格を外した表層が見出し語に一致する架空企業（北陸精機株式会社）も同種。一般名詞の残り部分を公知としない絞り込みは Phase 2 の検討項目。

wikinews で保持されなかった公知は、複合形（京都府京都市、旧京都府警本部、九州新幹線新大牟田駅。§3.3 の末尾要素照合で改善可能）と、英字略称ルールで弾かれた ANA・NHK・UAE・JAXA（10 件）である。後者は架空略称 KTR・NDS・NKS の衝突（私人文書 3 件）を塞ぐ代償で、見出し語の英字略称は 3 文字 13,188 件・4 文字 15,397 件と衝突リスクに差が無いため、安全側の「4 文字以下は公知としない」を維持した。

保持された私人 PERSON 18 件の原因と対策:

| 原因 | 例 | 対策 |
|---|---|---|
| 「議員」肩書きルール | 乙葉寺しずく議員、蒼波議員、網代 汐里議員、樫尾 誠一郎議員（架空の議会だより） | 議員は公人という方針に沿った挙動。ただし設定で外せるようにする（§7） |
| 実在の同名人物との衝突 | 無名の同名実在人物（sitelinks 1、§4.5）、ハン・ソヒ（25）、ジョナサン・リー | Wikidata sitelinks 閾値（§4.5）。閾値以上の著名人と同姓同名の私人は残存リスク → strict で回避 |
| 名前の分裂・地名との誤認 | 「生源寺 タキ」→ 生源寺が寺院名で FACILITY_PUBLIC、「網代 汐里」→ 2 分割 | Refiner 追加（§3.6） |

保持された ORG / FACILITY / LOCATION は、公的機関（仙台地方裁判所・公取委・経産省・西宮商工会議所）、実在の都市・駅・施設（横浜・姫路・恵那・北海道・青葉駅・幕張メッセ・太宰府天満宮）、実在チェーン（文栄堂）で、いずれも新定義では保持が正しい。例外は **架空企業の英字略称（NKS・KTR・NDS）** が見出し語（NDS = Nintendo DS 等）と衝突した 3 件で、「4 文字以下の英字のみの表層は公知としない」規則を §3.3 に加えて塞ぐ。

プロトタイプ初版にあった「文書内に私人がいなければ残す」分岐は、NER の型誤り（「田淵案件」→ ORG）や架空企業（株式会社リグレット・テクノロジーズ、上茅野倉庫）をそのまま通していた（ORG 保持 23/86、17/41、35/247）。分岐を外した最終ルールで上表の水準に下がり、6 例（§0）の出力は変わらなかった。

## 5. 実現可能性・UX の評価

- **性能**: ハッシュ照合は 1 件あたり μs オーダーで、NER（約 5ms/文書）に対して無視できる。CPU スループット要件は維持される。
- **配布**: 判定データ約 20MB はライブラリに同梱せず、利用者が生成して渡す。strict のみの利用者には不要。ダンプ更新は年 1〜2 回で十分（見出し語の増分は小さい）。
- **透明性**: サブタイプが `TransformedEntity.entity_type` に出るため、保持理由が結果から追える。
- **モデル**: 再学習不要。将来 PERSON_PUBLIC を NER ラベルにする案は、名前の暗記で汎化を損ねる恐れがあるため採らない。
- **LLM による判定**（肩書きも許可リストも無いときの公私判断）: 精度は高いが CPU 要件とコストに合わない。オフラインのバッチ後処理として任意の Annotator に差し込める余地だけ残す。
- **残るリスク（standard）**: (1) 著名人と同姓同名の私人が残る、(2) 公知の場所と私人が手掛かり語なしで共起する文、(3) 「安倍総理と会食した△△さん」のように公人との共起そのものが私人の準識別子になる文。(3) は△△を匿名化しても会食の事実で絞り込まれ得る。これらは仕様として明記し、許容できない用途は strict を使う。

## 7. 未決事項（既定値で実装し、設定で変更可能）

1. **ライブラリの既定レベル**: 提案は strict（現行互換・安全側）。LLM 学習データ用途では利用側で standard を指定する。
2. **「議員」の扱い**: 提案は公人（国会・地方議会とも）。地方議員を私人扱いにしたい場合は肩書きリストから外す設定を用意する。
3. **法人名**: 新定義では個人情報ではないため standard で保持対象（公知のもののみ。無名企業は現行どおり置換）。機密として全社名を隠したい用途は strict。
4. **Wikidata sitelinks の閾値**: 初期値 10。評価セットで調整する。
5. **公人と共起する私人（§5 のリスク 3）**: 仕様として明記し許容するか、standard でも公人を置換する派生レベルを設けるか。
